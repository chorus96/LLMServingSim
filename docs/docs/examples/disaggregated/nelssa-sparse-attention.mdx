# NELSSA sparse attention on HC-PNM

> **What this demonstrates:** multi-million-token decode on a
> high-capacity PNM (HC-PNM) module using **dynamic sparse attention** —
> streaming only the top-k selected KV tokens instead of the whole cache.

[NELSSA](https://doi.org/10.1109/LCA.2025.3624272) (SK hynix, IEEE CAL
2025, *"PNM Meets Sparse Attention"*) targets the extreme resource
imbalance of long-sequence decode: the KV cache demands enormous memory
capacity and bandwidth, yet the attention compute is tiny. Its insight is
to pair a **high-capacity PNM** module (cheap DDR5, huge capacity, modest
~200 GB/s internal bandwidth) with **dynamic sparse attention** (keep only
the ~2% of tokens that matter), so the low bandwidth is no longer the
bottleneck.

LLMServingSim models this as two composable pieces:

1. **HC-PNM hardware** — a DDR5 PNM module config
   (`configs/pim/DDR5_1TB_6400_pim.ini`: 4-channel DDR5-6400, 1 TB,
   ~200 GB/s), attached like any other PIM substrate.
2. **Sparse attention** — the `--sparse-attention-ratio` flag makes the
   PIM attention kernel stream only `ceil(ratio × L)` selected tokens and
   adds a token-selection (vector-search) cost, instead of the full KV
   cache.

## Prerequisites

- Simulator container set up
- Bundled RTXPRO6000 profile for `meta-llama/Llama-3.1-8B`
- The `DDR5_1TB_6400_pim` PIM config (bundled in `configs/pim/`)

## Cluster config

`configs/cluster/single_node_nelssa_hcpnm_instance.json`: the HC-PNM
module is wired in via `cpu_mem.pim_config`, and attention offloading is
enabled per-instance:

```json title="single_node_nelssa_hcpnm_instance.json (excerpt)"
{
  "cpu_mem": {
    "mem_size": 1024,
    "mem_bw": 205,
    "mem_latency": 0,
    "pim_config": "DDR5_1TB_6400_pim"
  },
  "instances": [
    {
      "model_name": "meta-llama/Llama-3.1-8B",
      "hardware": "RTXPRO6000",
      "npu_mem": {"mem_size": 96, "mem_bw": 1597, "mem_latency": 0},
      "tp_size": 1,
      "enable_attn_offloading": true
    }
  ]
}
```

The same config serves as both experiment arms:

- **Hermes-style HC-PNM baseline** (full attention): run **without**
  `--sparse-attention-ratio`.
- **NELSSA** (sparse attention): run **with** `--sparse-attention-ratio`.

## Run

```bash
# NELSSA: 2% dynamic sparse attention on the HC-PNM module
python -m serving \
  --cluster-config 'configs/cluster/single_node_nelssa_hcpnm_instance.json' \
  --dtype bfloat16 --block-size 16 \
  --enable-attn-offloading \
  --sparse-attention-ratio 0.02 \
  --dataset 'workloads/example_trace.jsonl' \
  --output 'outputs/nelssa_run.csv' \
  --log-level WARNING
```

Drop `--sparse-attention-ratio` to get the full-attention HC-PNM baseline
for an A/B comparison on identical hardware.

## Baselines: HC-PNM vs the CXL-PNM (HB-PNM) baseline

NELSSA compares its HC-PNM (`--no`-sparse = Hermes) against a **CXL-PNM [4]
baseline** — an *HB-PNM* (High-Bandwidth PNM) module: stacked LPDDR5X,
~1.1 TB/s (≈5.5× the HC-PNM DDR5 module) but only **128 GB**. Its config,
`configs/cluster/single_node_cxlpnm_baseline_instance.json`, uses the
`LPDDR5_HBPNM_128GB_pim` device and runs **full** attention (no sparse
ratio):

```bash
python -m serving \
  --cluster-config 'configs/cluster/single_node_cxlpnm_baseline_instance.json' \
  --dtype bfloat16 --enable-attn-offloading \
  --dataset 'workloads/example_trace.jsonl' \
  --output 'outputs/cxlpnm.csv' --log-level WARNING
```

Three arms on the same model/hardware (short-context smoke test,
Llama-3.1-8B, per-token TPOT):

| Arm | Device | Attention | TPOT |
| --- | --- | --- | --- |
| CXL-PNM [4] (HB-PNM) | LPDDR5X, 1.1 TB/s, **128 GB** | full | 14.9 ms |
| HC-PNM full (Hermes) | DDR5, 200 GB/s, 1 TB | full | 29.6 ms |
| NELSSA | DDR5, 200 GB/s, 1 TB | sparse 2% | 19.0 ms |

This reproduces the paper's trade-off: the HB-PNM's bandwidth makes full
attention **fast per token** at short context, but its **128 GB capacity**
caps sequence length — long-context runs OOM (the paper's Fig. 5 'X'
markers), which is exactly where NELSSA's 1 TB HC-PNM + sparsity keeps
running.

### Sweeping sequence lengths (Fig. 5)

`scripts/nelssa_fig5_sweep.py` automates the three-arm comparison across a
range of prompt lengths and prints **relative decode throughput**
(normalised to Hermes, from Mean TPOT so it reflects the decode step) with
`X` for OOM — the paper's Fig. 5 view:

```bash
python scripts/nelssa_fig5_sweep.py \
  --lengths 3072,6144,12288 --num-requests 4 \
  --out-csv outputs/fig5_sweep.csv --out-plot outputs/fig5_sweep.png
```

```text
NELSSA Fig. 5 -- relative decode throughput (normalised to Hermes)
arm                           3K        6K       12K
Hermes (HC-PNM full)       1.00x     1.00x     1.00x
NELSSA (HC-PNM sparse)     1.53x     1.83x     2.03x
CXL-PNM (HB-PNM full)      1.92x     2.20x     2.29x
```

The advantage over Hermes **grows with sequence length** (NELSSA
1.53→2.03×, HB-PNM 1.92→2.29× from 3K→12K) — the paper's key trend, since
decode attention takes a larger share of the step as KV grows. Use a batch
(`--num-requests`) and long-enough prompts so the decode attention — where
the arms differ — dominates the step. A PNM capacity override
must stay ≥ its DIMM size (256 GB for the DDR5 HC-PNM, 16 GB for the
LPDDR5X HB-PNM) or PIM disables; OOM markers therefore appear at large
lengths, so faithful multi-hundred-K/M-token sweeps are slow.


:::note Modeling the capacity limit
With attention offloading the KV cache lives on the PNM, so the PNM
device's capacity — not the GPU's — bounds the KV budget: it is sourced
automatically from the PNM tier (`cpu_mem` for a remote-attached PNM,
`cxl_mem` for a CXL-attached one), while weights stay in GPU HBM. A
sequence whose KV exceeds it stalls/OOMs. So the HB-PNM baseline's 128 GB
(`cpu_mem.mem_size: 128`) caps KV where the HC-PNM's 1 TB keeps going —
for Llama-70B, ≈400K tokens vs ≈3.2M — with no manual `npu_mem` sizing.
The device **bandwidth** is modeled by the PNM attention coefficients; the
**capacity** by the KV budget. Both PNM baselines share the same PCIe 5.0
interconnect (`link_bw: 64`), matching the paper. (Without offloading, the
KV budget stays the ordinary `npu_mem − weight`.)
:::

### CXL-attached PNM

By default the PNM attaches to the node's `cpu_mem` (remote) tier and its
trace targets `REMOTE:` locations. To model a **CXL-attached** PNM instead
(the original CXL-PNM [4] platform is a CXL.mem device), put `pim_config`
inside the top-level `cxl_mem` block. The PNM's near-memory compute and
memory then live on the CXL tier: `config_builder` sizes the CXL tier's
bandwidth/latency and `pim-channels` from the device, and PIM attention
targets `CXL:{node}.{ch}` locations. `cpu_mem` stays an ordinary remote
tier. See `configs/cluster/single_node_nelssa_cxl_pnm_instance.json`:

```json title="single_node_nelssa_cxl_pnm_instance.json (excerpt)"
{
  "cxl_mem": {
    "mem_size": 1024, "mem_bw": 205, "mem_latency": 250,
    "num_devices": 4, "pim_config": "DDR5_1TB_6400_pim"
  },
  "nodes": [{
    "cpu_mem": {"mem_size": 512, "mem_bw": 256, "mem_latency": 0},
    "instances": [{ "...": "enable_attn_offloading: true" }]
  }]
}
```

Everything else (sparse ratio, GPU-local split, index build) works
identically — only the PNM's memory tier and trace location tags change.

**KV capacity is sourced from the PNM tier.** With attention offloading the
KV cache lives on the PNM, so its capacity — not the GPU's — bounds the KV
budget: the scheduler admits KV up to the PNM's `mem_size` and a sequence
that exceeds it stalls/OOMs (weights stay in GPU HBM). This is automatic
for both attachments — `cxl_mem.mem_size` for a CXL-attached PNM,
`cpu_mem.mem_size` for a remote-attached one — with no manual `npu_mem`
sizing. A 128 GB PNM caps KV where a 1 TB one keeps running, reproducing
the CXL-PNM vs HC-PNM capacity trade-off directly. (A CXL PNM can spill
overflow to the distinct host CPU tier; a remote PNM, being its own bottom
tier, backs off instead. Without offloading, the budget stays the ordinary
`npu_mem − weight`.)

## Flags

| Flag | Meaning |
| --- | --- |
| `--sparse-attention-ratio` | Fraction of KV tokens kept per decode step (e.g. `0.02` = 2%). Unset → full attention. Requires `--enable-attn-offloading`. |
| `--sparse-vector-search-nprobe` | IVF lists probed during token selection (vector search). Higher = more recall and higher selection cost. Default `32`. |
| `--attention-local-window` | Recent decode tokens kept in GPU HBM and attended on the GPU (overlapping PIM). Default `0` (all decode KV on PIM). |
| `--attention-sink-tokens` | Leading attention-sink tokens kept in GPU HBM (added to the local window). Default `0`. |
| `--sparse-index-build` / `--no-sparse-index-build` | Model the RetrievalAttention vector-index build at prefill. Default on (only active with a sparse ratio). |
| `--sparse-index-footprint-ratio` | Vector-index memory as a fraction of the KV cache (stored on the PNM, reduces KV capacity). Default `0.10`; `0` disables. Sparse mode only. |

### GPU-local KV split (recent + sink window)

NELSSA keeps *predictable* KVs — a recent-token window plus the leading
attention sinks — in fast GPU HBM, and offloads only the remaining bulk to
the PNM modules. The GPU attends its local window concurrently with the PNM
sparse attention, and the two partial results are combined with negligible
overhead. Enable it with:

```bash
python -m serving \
  --cluster-config 'configs/cluster/single_node_nelssa_hcpnm_instance.json' \
  --dtype bfloat16 --enable-attn-offloading \
  --sparse-attention-ratio 0.02 \
  --attention-local-window 1024 --attention-sink-tokens 4 \
  --dataset 'workloads/example_trace.jsonl' \
  --output 'outputs/nelssa_split_run.csv' --log-level WARNING
```

For each decode request of KV length `L`, the GPU handles a window of
`w = sink + recent` tokens and PIM handles the bulk `L − w`. The GPU
attends *all* decode windows in one batched operation that overlaps the
whole PNM phase, so the overlap is modeled at the batch level:

```
decode_attention_latency = max(pnm_time, gpu_local_batch)
```

where `pnm_time` is the busiest PIM channel's summed bulk work and
`gpu_local_batch` is a single batched NPU attention over every decode
window. In the trace this is emitted as pure-bulk PIM lines plus one NPU
node carrying only the residual `max(0, gpu_local_batch − pnm_time)`, so
the GPU work is never serialized per request. At multi-million-token scale
`w ≪ L`, so PIM stays the critical path and the split mainly guarantees the
predictable tokens are always attended (accuracy) rather than changing
latency. For shorter sequences that fit inside the window, attention runs
entirely on GPU HBM and is faster.

## The model

For a decode request whose KV cache holds `L` tokens, PIM attention
latency becomes (per the two NELSSA compute-unit modes):

- **M2 — sparse attention GEMV** over `k = ceil(ratio × L)` selected
  tokens, reusing the bandwidth-bound linear model but streaming `k`
  tokens instead of `L`.
- **M1 — token selection** via IVF vector search. Following the paper's
  √N heuristic, `n_list = round(√L)` and the `nprobe` probed lists hold
  ~`nprobe × √L` key vectors; selection reads keys only (half the
  per-token streaming of full attention).

Both live in `serving/core/pim_model.py::get_sparse_pim_latency`.

### Index build (prefill, upfront)

RetrievalAttention builds a per-layer IVF vector index over the prefilled
KV cache and offloads it to the PNM modules — a one-time upfront cost at
prefill (`--sparse-index-build`, on by default when a sparse ratio is set;
disable with `--no-sparse-index-build`). Inserting the new KV vectors into
an index with `n_list = round(sqrt(kv_size))` centroids costs one
`head_dim`-wide distance per (vector, centroid) pair, i.e. `O(N^1.5)` over
the sequence. This is **compute-bound**, so it is sized by the PNM engine's
throughput `peak_flops = mem_bw × operational_intensity` (the DDR5 module's
`operational_intensity = 8` gives ~1.6 TFLOPS at 204.8 GB/s — exactly the
paper's bandwidth-saturating engine). It lands on the **prefill critical
path** (raising TTFT), not on decode. It is negligible for short prompts
(~10 ms of TTFT at a 20K-token prompt on Llama-3.1-8B) and grows toward
seconds for multi-million-token prompts — an upfront cost amortized over
the whole decode. Model: `serving/core/pim_model.py::get_index_build_latency`.

The index also **occupies PNM memory** alongside the KV cache, reducing the
effective KV capacity (`--sparse-index-footprint-ratio`, default `0.10` =
the index is 10% of the KV size; `0` disables). Since both scale with
tokens, the KV budget shrinks to `PNM_capacity / (1 + ratio)` — e.g. a 1 TB
HC-PNM holds ~930 GB of KV plus its index. This lowers the OOM boundary
accordingly (`serving/core/memory_model.py`). Applies only in sparse mode.

## What's interesting

- **Speedup grows with sequence length.** Because sparse attention keeps
  a *fixed fraction* of tokens, the win over full attention widens as `L`
  grows — reproducing the paper's 11×–40× range over the HC-PNM
  full-attention (Hermes) baseline from ~16K to multi-million tokens.
- **Robust to the selection ratio.** Raising the ratio from 2% to 10%
  grows per-token decode latency by only ~2–3× (the paper's Fig. 6
  sensitivity), not 5×, because the fixed selection + pipeline overhead
  amortizes.
- **Capacity is decoupled from the GPU.** The 1 TB HC-PNM module holds KV
  caches far beyond HBM limits; sparse attention keeps the module's modest
  bandwidth from becoming the new bottleneck.

:::caution Derived, not measured
This 70B profile is **analytically scaled** from the measured
Llama-3.1-8B profile (per-layer FLOP/byte ratios), not captured from real

launch overhead, tensor-core tiling, and bandwidth effects are not
modeled, so absolute numbers are approximate — regenerate with a measured

## Modeling notes

- **Batch-level concurrency.** The GPU-local and PNM attentions overlap, so
  the step's decode-attention latency is `max(pnm_time, gpu_local_batch)`
  rather than their sum. The GPU work is a single batched attention over all
  decode windows (not serialized per request), and only its un-hidden
  residual is added to the critical path. The result-combine is treated as
  negligible (per the paper). PIM and GPU energy are still tracked on their
  own devices.
- **Index build is on the prefill critical path.** The RetrievalAttention
  index build is emitted as a per-layer compute node during prefill (raising
  TTFT), sized by the PNM compute engine. Because the Chakra converter
  assumes PIM blocks only appear in decode, it is emitted as a compute node
  rather than a PIM block; its energy is still attributed to the PNM engine.
- **What's not modeled yet.** The GPU-local batch uses the mean window across
  decodes as its `kv_decode` key, and the index build uses batch-summed
  `prefill_chunk` / `kv_size` (rather than per-request) for its `n_list`.
  These are refinements on top of the current model.
